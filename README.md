# TP Parser Service

Сервис парсинга технических паспортов железнодорожного пути необщего
пользования (`.doc` / `.docx` / `.pdf`) в JSON, структура которого
повторяет заголовки/подзаголовки «Инструкции о порядке обслуживания и
организации движения…». На выходе — **только извлечённые данные**.


## 🐳 Запуск через Docker (рекомендуемый способ)

### Требования
- [Docker](https://docs.docker.com/get-docker/)
- [Docker Compose](https://docs.docker.com/compose/install/)

## Запуск

```bash
# 1. Клонируем репозиторий
git clone https://github.com/IvSidGit/Practice_3_course
cd tp-service-parser-new

# 2. Собираем Docker-образ (первый раз или после изменений)
docker-compose build

# 3. Запускаем сервис в фоновом режиме
docker-compose up -d

# 4. Проверяем, что сервис работает
curl http://localhost:8000/health
# Ожидаемый ответ: {"status":"ok"}
```

## Проверка работы
```bash
# Проверка статуса контейнера
docker-compose ps

# Просмотр логов
docker-compose logs -f

# Проверка здоровья сервиса
curl http://localhost:8000/health
```

## Отправка файла на парсинг
```bash
# Отправить PDF/DOC/DOCX файл и сохранить результат
curl -F "file=@путь/к/файлу.pdf" http://localhost:8000/parse > result.json

# Пример с конкретным файлом
curl -F "file=@Техпаспорт_ООО_ЗЛП_2024.pdf" http://localhost:8000/parse > result.json
```

### Системная зависимость: LibreOffice

Для `.doc` сервис вызывает `soffice --headless --convert-to docx`. Нужен
установленный LibreOffice (`apt install libreoffice`) в контейнере/окружении
сервиса. `.docx` и `.pdf` конвертации не требуют.

## Архитектура

```
файл (.doc/.docx/.pdf)
        │
        ▼
converters.py        — определяет формат; .doc → .docx через LibreOffice
        │
        ▼
parsers/docx_parser.py   ИЛИ   parsers/pdf_parser.py
        │                              │
        └──────────────┬───────────────┘
                        ▼
              RawDocument (parsers/base.py)
     единое представление: абзацы + таблицы по порядку,
     каждая таблица — с подписью и распознанной темой
     ('ballast_type', 'path_lengths', 'cargo_capacity', ...)
                        │
                        ▼
        extraction/normalize.py
     regex-экстракторы, заточенные под устойчивые формулировки
     типовых бланков → TechPassportData (models.py)
                        │
                        ▼
        extraction/section_mapping.py
     раскладывает нормализованные данные по заголовкам инструкции,
     помечает каждый лист available/unavailable + источник
                        │
                        ▼
                  итоговый JSON
```

Почему именно так:

- **`RawDocument` как общая точка стыковки форматов.** docx даёт честную
  таблицу (python-docx), PDF даёт только линейный текст с примерным
  порядком чтения — восстановление табличной сетки через pdfplumber на
  этих бланках разваливается из-за рамки штампа и вертикальных подписей
  сбоку листа (проверено экспериментально, см. `parsers/pdf_parser.py`).
  Вместо того чтобы городить два независимых пайплайна извлечения, весь
  код после `RawDocument` работает одинаково для обоих форматов:
  PDF-таблица — это `RawTable` с одной "псевдострокой", содержащей текст
  блока, docx-таблица — `RawTable` с честной сеткой ячеек.
- **Таблицы адресуются по смысловой теме заголовка, а не по номеру.**
  `RawDocument.tables_by_topic()` (см. `parsers/base.py::TOPIC_KEYWORDS`)
  сопоставляет таблицу теме ('ballast_type', 'sleepers', 'path_lengths', …)
  по ключевым словам в подписи — независимо от того, что одна и та же по
  смыслу таблица в разных шаблонах имеет разный номер (например,
  «Закрепление от угона» — Таблица 3.12 у АО «ВНИИЖТ», но Таблица 3.5 в
  шаблоне «ТЧГП»). Это единственный способ поддержать несколько шаблонов
  одним набором экстракторов, не дублируя логику под каждый номер таблицы.
  `tables_by_number()` тоже доступен (для отладки), но `extraction/normalize.py`
  везде использует `tables_by_topic()`.
- **Подпись таблицы распознаётся в двух форматах.** Шаблоны АО «ВНИИЖТ»/
  ООО «Забтранспроект» пишут подпись одной строкой
  («Таблица 3.2 – Толщина балластного слоя»); шаблон «ТЧГП» разносит её
  на два абзаца подряд (сначала «Толщина балластного слоя», затем
  отдельным абзацем «Таблица 3.2»). `docx_parser.py::_build_caption`
  собирает оба варианта в одну подпись перед тем, как её увидит
  `tables_by_topic()`.
- **Многопутевые PDF-таблицы разбиваются по известным номерам путей.**
  На бланке нескольких путей одного предприятия PDF-парсер отдаёт всю
  таблицу «Данные по длине путей» ОДНОЙ псевдострокой — данные всех
  путей склеены в одну строку текста. `extraction/normalize.py::
  _split_blob_by_known_paths` режет эту строку на сегменты по позициям
  номеров путей, извлечённых с титульного листа (`Путь №71, 71а, МСУ
  262-270` → `['71', '71а', 'МСУ 262-270']`), включая устойчивость к
  случаю, когда составной номер («МСУ 262-270») разорван посторонним
  текстом в самой PDF-линеаризации — тогда используется короткий якорь
  (первое слово, «МСУ»), результат сопоставляется обратно с полным
  номером.
- **Если экстрактор не уверен — он возвращает `None`, а не догадку.**
  Для последующей ИИ-генерации подставленное неверное число опаснее,
  чем отсутствующее поле: галлюцинацию из текста потом трудно заметить,
  а `null` в JSON — сигнал, что это поле нужно проверить/заполнить вручную.
  В частности: если у пути в поле «полезная длина» стоит прочерк, а не
  число, сервис не пытается угадать вторую цифру откуда-то ещё (например,
  из итоговой суммы по предприятию) — оставляет `null`.

## Формат вывода

```jsonc
{
  "meta": { "source_file": "...", "company_name": "...", "station_name": "...", "path_numbers": ["2"] },
  "section_1_general_characteristics": {
    "1.1": { "available": true,  "data": {...}, "source": "..." },
    "1.5": { "available": true,  "data": [{"device_type": "...", "picket": "ПК1+04,86", ...}], "source": "..." },
    "1.7": { "available": false, "data": null, "source": null, "note": "почему недоступно" },
    "1.9": {
       "cargo_fronts": { "available": true, "data": [ {...ГФ1}, {...ГФ2} ] },
       "1.9.1": { "available": false, "note": "..." }
    },
    ...
  },
  "section_2_supply_removal_procedure": { "2.1": {...}, ... },
  "unmapped_raw_tables": { "3.9": "необработанный текст таблицы для ручного добавления экстрактора" }
}
```

Каждый лист — стабильный контракт `{available, data, source, note?}`, чтобы
компонент генерации текста мог единообразно решать: строить фразу из `data`
или (при `available=false`) брать значение из другого источника.

`unmapped_raw_tables` — не мусор, а страховка: туда попадает необработанный
текст всех распознанных таблиц техпаспорта. Если для какой-то таблицы нет
специализированного экстрактора, данные не теряются молча — они видны в
сыром виде и годятся как отправная точка для нового экстрактора.

## Ограничения (важно прочитать перед интеграцией)

1. **Не все заголовки инструкции выводимы из техпаспорта в принципе.**
   Техпаспорт описывает путь как объект инфраструктуры (границы, длины,
   устройства, грузовые фронты). Разделы про регламент взаимодействия —
   ответственные лица, номера телефонов, формы уведомлений (ГУ-2вВЦ и т.п.),
   порядок манёвров, включение автотормозов, порядок закрепления — берутся
   из отдельного набора документов (приказ предприятия, договор со
   станцией, местная инструкция по маневровой работе), которого нет во
   входном файле. Такие листы сервис честно помечает
   `"available": false` с пояснением в `"note"`, а не выдумывает данные.
   Полный список см. в `section_mapping.py::_NOT_IN_TECH_PASSPORT` и
   комментарии к каждому `_leaf(...)`.

2. **Уклон и радиус кривой (п. 1.6.2) не извлекаются.** В обоих
   образцах эти величины существуют только как подписи на чертеже
   продольного профиля/плана пути (векторная графика внутри PDF/DOCX),
   а не как текстовое или табличное значение. Надёжное извлечение
   потребует отдельного модуля работы с геометрией чертежа
   (см. «Точки расширения» ниже).

3. **PDF-извлечение менее точное, чем DOCX**, потому что pdfplumber не
   восстанавливает табличную сетку этих бланков (боковой штамп «Инв. №»,
   «Взам. Инв. №», «Подп. и дата» ломает порядок текста при линеаризации).
   Экстракторы вытягивают значения по регэкспам с защитными проверками
   (например, если внутри "найденной" границы пути затесалась дата или
   подпись — значение отбрасывается как недостоверное, а не отдаётся с
   браком). Для заголовков 1.3–1.5, которые берутся из связного текста
   «ОБЩИЕ СВЕДЕНИЯ» (не из таблиц), качество на PDF такое же высокое,
   как на DOCX — это проверено на образцах.

4. **Многопутевые предприятия поддержаны, но с оговорками.** Основной
   сценарий (несколько путей в одной таблице «Данные по длине путей»)
   покрыт и проверен на объектах с 2–4 путями (ООО «БИЛУГА», ИП
   Цивинский, ООО «ЗаЛП», ОАО «Читаоблгаз»), включая PDF, где вся
   таблица приходит одной строкой текста (см. «Архитектура» выше). Тем не
   менее: если у пути отсутствует одно из двух значений длины (стоит
   прочерк вместо числа), сервис не извлекает и второе, оставшееся —
   отдаёт `null` по обоим, чтобы не приписать путю чужое число (это
   безопасное, но заведомо неполное поведение — см. пример ЗаЛП, путь
   «МСУ 262-270» в тестах). Метаполе `meta.path_numbers` (список номеров
   путей с титульного листа) при отсутствии чёткой строки «Путь №…» на
   титуле (характерно для шаблона «ТЧГП») может остаться пустым или
   зацепить чужой номер из текста «Место примыкания» — это не критично,
   поскольку сами данные по путям (`1.6.path_lengths.data.paths`) берутся
   из таблиц техпаспорта, а не из этого метаполя.

5. **Проверено на трёх шаблонах бланков** (АО «ВНИИЖТ», ООО
   «Забтранспроект», шаблон с маркировкой «ТЧГП» — инвентарный номер вида
   «ТЧГП 0424-02»). Если проектная организация использует четвёртый
   шаблон с другими формулировками лейблов — часть экстракторов может не
   сработать (вернёт `None`, не упадёт). См. `unmapped_raw_tables` как
   отправную точку для быстрой донастройки под новый шаблон.

## Точки расширения

- **Новая таблица техпаспорта → новый заголовок инструкции.**
  Добавьте тему в `TOPIC_KEYWORDS` (`parsers/base.py`), функцию
  `extract_*` в `extraction/normalize.py`, положите результат в
  `TechPassportData` (`models.py`), прокиньте в
  `extraction/section_mapping.py::build_instruction_json`. Все
  распознанные по теме таблицы уже лежат в `raw.tables_by_topic()` —
  не нужно трогать парсеры форматов.
- **Координатное восстановление PDF-таблиц.** Если точности регэкспов
  на линейном тексте недостаточно (в первую очередь это ведомость
  стрелочных переводов — на объектах со стрелками может быть
  многоколоночной), добавьте модуль на `page.extract_words()` с
  кластеризацией по X-координате в `parsers/pdf_parser.py`, не трогая
  остальной пайплайн — `RawTable.rows` просто станет "честной" сеткой
  вместо одной псевдостроки, и все использующие `_row_text()`
  экстракторы получат более точные данные автоматически.
- **Разбор чертежа плана/профиля (п. 1.6.2).** Отдельный модуль,
  читающий векторные подписи (уклон в ‰, радиус R, длина элемента) со
  страницы PDF или из EMF/WMF-вставки в DOCX — вне рамок текущей
  реализации, see `section_1["1.6"]["1.6.2"]` note в коде.
- **Другой шаблон бланка.** Лейблы для распознавания вынесены в
  константы в начале `extraction/normalize.py`
  (`_GENERAL_LABELS`, `SPECIALIZATION_KEYWORDS`, `_DESIGN_ORG_BLOCKLIST`)
  и `parsers/base.py::TOPIC_KEYWORDS` — для нового шаблона обычно
  достаточно расширить эти списки, не меняя логику. Формат подписи
  таблицы (однострочный / двухабзацный) определяется автоматически в
  `docx_parser.py::_build_caption`; если появится третий вариант оформления
  подписи — добавить его туда же.
